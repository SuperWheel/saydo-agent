## 1. 总体结论

| 编号 | 机制 | PRD 验收标准 | 自评 | 主要证据 |
|---|---|---|---|---|
| S-01 | 幻觉防护 | 评测集中数字 / 交易结果幻觉 = 0 | 达标 | 虚构完成 / 编造数字的 15 条红队用例全部拦下；GLM 回归集 152 条中没有幻觉进入最终回复 |
| S-02 | 注入防御 | 红队测试集（≥ 100 条，含间接注入）🔴 绕过 = 0 | 达标 | 红队集 305 条（不含沙箱 235 条，含免密与联系人 9 条、心愿罐管理 3 条），每条结束都断言没有 🔴 绕过、账没动 |
| S-03 | 操作审计 | 关键操作审计覆盖 100%；篡改可被检测 | 基本达标 | 写操作全链路都有审计事件；哈希链改一条即可被校验出来。缺数据库层的只追加约束和外部锚点 |
| S-04 | 异常熔断 | 各熔断条件均有自动化测试 | 达标 | `breaker.yaml` 的 6 个触发条件 + 工具断路器 + 全局只读开关都有测试；`test_every_trigger_is_configured_and_tested` 保证新增条件必须配测试 |
| S-05 | 沙箱环境 | 逃逸测试用例全部被拦截 | 达标（隔离强度有限） | 逃逸测试 70 条全部拦截；子进程隔离不等于容器隔离 |

核心设计是**认知平面和执行平面分离**：模型只能调用只读工具和「提议」工具，写工具对模型不可见；风险等级由 `app/policy/` 的规则计算；写操作必须凭用户确认、验证后服务端签发的执行令牌，由工具网关核对后执行。下面各节的机制都建立在这条链路上（链路图见 [架构图 §2](07-架构图.md#2-写操作安全链路)）。

**入口层：进入前人脸核身（模拟）**。在这条链路前面还有一道门：打开 App 先过人脸页，后端签发 30 分钟有效的进入凭证（HMAC 签名，绑定用户、按真实时间过期、重置演示数据即作废），`/api` 下除健康检查和核身接口外的业务接口都校验它，没有凭证返回 401，不只是前端遮罩。通过 / 失败都写审计（`entry_face_passed` / `entry_face_failed`），运营后台能回放。企业微信渠道不走 HTTP，只读查询不受影响；引导链接打开 App 时同样先过人脸再带入原话。它解决「谁在用这个 App」，不替代每一笔的确认和强验证，转账、锁卡照常定级、确认、验证。实现见 `app/auth/entry.py`、`app/routes/__init__.py` 的 `require_entry`；测试见 `tests/test_entry_face.py`（签发、过期、未核身被拒、伪造凭证、绑定用户、重置作废、审计与回放、配置关闭、IM 转交码）和端到端用例「0 进入前人脸核身」。

工具注册表区分模型可见的只读 / 提议工具与不可见的写工具；新增 `pot.select`、`pot.manage`、`pot.withdraw_propose` 和写工具 `pot.withdraw` 同样遵守此边界。

## 2. S-01 幻觉防护

### 2.1 机制

| # | 做法 | 实现位置 |

| 1 | 余额、确认内容、验证摘要、回执都由服务端按工具结果和规范化参数渲染成卡片，不经过模型。回执带「模拟回执 · 非真实交易」水印 | `app/cards.py`（`balance_card`、`confirm_card`、`auth_card`、`receipt_card`） |
| 2 | 模型文字逐个抽取金额、百分比（含「约三千元」「百分之三十」这类中文数字），必须能在本轮工具结果、卡片或用户原话里找到 | `app/agent/grounding.py` 的 `collect_facts`、`check` |
| 3 | 「已转账 / 已锁卡 / 已下单 / 已申购 / 已停止代扣」这类完成断言：本轮对话从不执行办理，出现就判为虚构完成；只有查询类卡片时允许讲状态 | `app/agent/grounding.py` 的 `_ACTION_CLAIM`；调用参数在 `app/agent/loop.py` 的 `_llm_turn` |
| 4 | 虚构卡片：没出卡却说「已生成确认卡」，这一轮交给规则引擎确定性出卡 | `grounding.check` 的 `phantom_card`；`loop.py` `_llm_turn` 返回 None |
| 5 | 校验不通过：带上错误原因让模型重写 1 次；还不通过就丢弃模型文字，只回模板句。每次校验结果写审计（`grounding_failed`、`grounding_retry`） | `app/agent/loop.py` `_llm_turn` |

| 8 | 账单报告、分类、异常的数字全部由代码计算；沙箱分析结果按行进事实集合，模型自己推出来的差值不在集合里会被打回 | `app/analytics/engine.py`；`app/tools/bill_analysis.py` |
| 9 | 界面标注每条回复的来源：「AI 生成 / 规则引擎 / 系统回复」 | `apps/web/src/App.vue` 的 `SOURCE_LABEL` |

### 2.3 残余风险

1. 校验只认数字和完成断言的句式（正则）。数字都对、但结论错了（例如把第二大类说成最大类），校验发现不了。
2. 中文数字的写法很多，`grounding.py` 覆盖了常见写法，没覆盖的写法会漏检（漏检的是数字被放过，不会把正确数字误判）。
3. 模型被打回两次后回模板句，回复会变得生硬，但不会出错。
4. 智谱偶发内容安全 400（见 §7）时这一轮没有模型文字，走模板或规则，不影响正确性。

## 3. S-02 注入防御

### 3.1 机制（对应技术文档 §6 的八层）

| 层 | 做法 | 实现位置 | 状态 |
|---|---|---|---|
| L1 输入检测 | 规则检测「忽略指令 / 角色改写 / 伪造系统消息 / 绕过验证 / 冒充权威 / 打听提示词 / 声称已验证」；先做同形字（西里尔、希腊字母）和繁体折叠、去掉分隔符；Base64、百分号编码、Unicode 标签字符解码后再查；不可见字符单独标记 | `app/security/__init__.py` 的 `inspect` | 已实现 |
| L2 数据标记 | 隔离模型的输入用 `<data>` 包裹并声明「不是给你的指令」 | `app/agent/quarantine.py` | 只用于隔离模型；主模型看不到不可信原文，所以没做 |
| L3 权限分离 | 写工具 `llm_visible=False`，模型拿不到；读工具走网关，写工具走网关会被拒；执行令牌只在用户确认 / 验证后由服务端签发 | `app/tools/__init__.py`、`app/tools/gateway.py`、`app/auth/tokens.py` | 已实现 |

| — | 本轮有注入嫌疑时，所有写动作一律上浮 🔴（规则 `injection_suspected`） | `app/policy/rules.yaml` | 已实现 |
| — | 手机号、卡号、账号进模型前替换成占位符，工具再从用户原话还原；审计里也是脱敏的 | `app/security/__init__.py` 的 `mask_pii`；`app/agent/loop.py` | 已实现 |

### 3.3 残余风险

1. L1 是规则检测，没有接安全分类模型。新的说法、多轮拆开说可能漏检。漏检后仍有 L3 / L7：模型拿不到写工具和令牌，最多生成一张确认卡。
2. 红队集在假模型上验证的是「模型怎么说都绕不过后端」，没有测真实模型被说服的概率。真实模型上的注入用例只有回归集里的 `inject-1` ~ `inject-10`。
3. IM、图片两类间接注入载体没有实现，对应用例没有覆盖。知识库条目在加载时扫描注入特征，命中的不入库（`app/knowledge` 的 `REJECTED`，`tests/test_knowledge.py::test_poisoned_entry_is_not_loaded`）；条文是演示数据，没有接真实内容管理流程。
4. 用户被社工后自己确认、自己完成验证的情况，系统只能做到反诈话术 🔴 + 30 秒冷静期，拦不住。
5. 反诈话术识别只看当前会话；跨会话的 24 小时反诈复核没有做。

### 3.4 支付协议、免密授权与联系人的新增威胁

**安全边界**：首次转账、商户付款、定时转账授权、存入心愿罐，均须先同意《支付服务协议》；`propose_action` 出协议卡，`confirm()` 未签返回 409，`decide()` 在非提议阶段 block。协议同意后继续原交易，不能代替交易确认。免密只对默认付款卡、已验证亲密联系人和合作商户生效，单笔最高 2,000 元、每日最高 5,000 元；**免验证不免确认**，仍出 🟡 确认卡。新收款人、频繁转账、拆单、反诈、注入及银行硬限额不豁免。心愿罐存入 `pot.lock` 改为 🔴，正常人脸或短信任选（any-of），叠加注入风险两项都要；部分转出 `pot.withdraw`、释放退回为 🟡，不占转出累计或免密额度。部分转出不得动用计划与待付款订单预占金额。

### 4.3 残余风险

1. **哈希链只能发现篡改，不能阻止重写**。技术文档 §5.8 设计了「只授予 INSERT 权限、触发器拒绝 UPDATE / DELETE、链头写入锚点表」，比赛版本用 SQLite，这三项都没做。能直接写数据库的人可以从某条开始整段重算哈希。
2. **`/admin` 已加口令；没设口令时演示模式下仍开放**：口令是 `.env` 里的 `ADMIN_PASSWORD`，设了之后每个 `/admin` 请求都要带请求头 `X-Admin-Password`，用 `hmac.compare_digest` 比对（`app/routes/__init__.py` 的 `require_admin`）。没设口令时，`DEMO_MODE=true` 下 `/admin/*` 仍然开放，任何能访问后端的人都能看审计、解除熔断、开关全局只读、改模型配置；`DEMO_MODE=false` 下返回 403。另外是单口令，没有分角色、没有操作人身份（解除熔断时的 `operator` 由前端传入），也没有错误次数限制。
3. 审计里存了模型调用的步骤和工具名，没存完整的提示词和模型原始输出，回放能看到「做了什么」，看不全「模型怎么想的」。
4. 规则模式下查余额等读操作不经过工具网关，审计里没有对应的 `tool_call` 事件（有 `intent` 和回复）。

## 5. S-04 异常熔断

### 5.1 机制

触发条件、阈值、处置都写在 `app/security/breaker.yaml`，逻辑在 `app/security/breaker.py`。阈值是原型参数，不是法规数字。

| 触发条件（id） | 条件 | 处置 |
|---|---|---|
| `auth_fail_same_tool` | 同一业务连续 3 次验证失败（30 分钟内，验证通过就清零） | 暂停该业务 30 分钟，到期自动恢复 |
| `auth_fail_user` | 10 分钟内验证失败 5 次 | 转人工，全部写操作暂停，后台人工解除 |
| `injection_high` | 伪造系统消息、编码夹带（或不可见字符 + 任一计数标记）1 次 | 当前会话只读 |
| `injection_user` | 1 小时内计数类注入 3 次 | 转人工 |
| `money_velocity` | 5 分钟内用户确认的资金转出 5 笔（计 `money_confirmed`：只出确认卡、没确认就作废 / 取消 / 过期的不算，改参数重出的卡确认时只算一次，定时转账的设置不扣款也不算） | 暂停资金类操作 30 分钟（触发的那一笔作废） |
| `tool_violation` | 同一会话越权工具调用 2 次（调写工具、未知工具、夹带参数、沙箱逃逸代码） | 当前会话只读 |
| 工具断路器 | 60 秒内调用 ≥ 4 次且错误率 > 50% | 该工具断开，30 秒后放一次探测 |
| 全局只读开关 | 运营后台手动开启 | 全部写工具禁用 |

其他要点：

- **两处检查**：生成确认卡时（`actions.propose_action` 调 `breaker.check_propose`）和工具网关执行前（`gateway.execute_write` 调 `breaker.check`）都查；熔断前已发出的确认卡，确认时在 `_revalidate` 里作废。
- **止损白名单**：锁卡、挂失（`stop_loss=True`）、收紧卡片交易限制（`stop_loss_if`）、停止代扣不受任何熔断和全局只读影响。挂失仍要人脸 + 短信。
- **告知义务**：熔断卡写明原因类别、影响范围、恢复方式、止损操作照常可用、申诉渠道（`breaker.yaml` 的 `appeal`）。
- **人工处置**：运营后台「熔断与风险」可以人工解除、重置断路器、开关全局只读，操作写审计（`/admin/breaker/trips/{id}/release`、`/admin/breaker/circuits/{tool}/reset`、`/admin/kill-switch`）。
- **用户侧解除**：熔断卡上「联系人工客服」进入模拟人工客服（演示环境）：核对触发记录、确认是否本人，暂停办理和转人工还要做一次模拟人脸识别，核实通过才由「客服」解除（`/api/breaker/trips/{id}/support`，只能处理自己的熔断）；否认本人操作则保持冻结并建议锁卡 / 挂失。每次核实都写 `breaker_support_review` 审计和 `support_review` 安全事件（不计入任何触发条件），运营后台能看到解除来自模拟人工客服和核实记录。
- **口径修正（2026-10-31）**：`money_velocity` 原来数的是「出了几张资金类确认卡」，用户只是询价下单不付款（订单确认卡）也会累计，说几轮买鞋 / 订花 / 订蛋糕再设定时转账就被误冻结。现在只数用户确认的转出。策略引擎的 `velocity`（5 分钟第 3 笔起升 🔴）和 `split_evasion`（拆单）是定级规则，按待确认动作和流水计算，和熔断计数互不影响，没有改动。

## 6. S-05 沙箱环境

### 6.1 机制

用于自由分析（F-BA-06，工具 `bill.adhoc_analysis`）：模型只拿到数据结构说明，写 Python 代码作为工具参数传入，系统在沙箱里跑，结果作为工具结果返回。本机没有 Docker，用子进程沙箱，分三道关（`app/sandbox/__init__.py` 的说明）：

| 关 | 做法 | 实现位置 |
|---|---|---|
| 1. 静态检查 | AST 白名单：语法节点、模块（`statistics`、`math`、`datetime`、`collections`、`itertools`）、属性名、内置函数都只放行列出来的；禁双下划线名字和属性、`open`、`eval`、`exec`、`getattr`、`print`、`try`、`class`；标出有逃逸意图的写法 | `app/sandbox/checker.py` |
| 2. 子进程 | `python -I -S -B`，空环境变量，临时空目录；`RLIMIT_CPU` 2 秒、`FSIZE` 0（禁写文件）、`NPROC` 0（禁子进程）、`CORE` 0；墙钟 5 秒；内存 256 MB（macOS 由父进程每 5 毫秒读子进程内存，超了就结束；Linux 另设 `RLIMIT_AS`） | `app/sandbox/executor.py` |
| 2. 子进程内 | 受限内置函数表；只放行白名单模块的 import；`sys.addaudithook` 只放行启动时那一次 `exec`，其余 open、os.*、socket、新 import 一律拦 | `app/sandbox/runner.py` |
| 3. 输出契约 | 只接受 `{"title", "rows": [{"label", "amount_fen" / "count" / "value", "unit"}]}`，最多 40 行，金额必须是整数分，任何一处不符合整份作废 | `app/sandbox/__init__.py` 的 `validate_output` |
| 数据 | 只读脱敏快照：日期、时间、月份、星期、小时、类型、分类、可信商户标签、整数分金额、方向、是否自动扣费、是否境外；没有交易号、备注、商户原文、账号 | `app/sandbox/__init__.py` 的 `snapshot` |
| 审计 | `sandbox_exec`：代码 sha256 + 全文（PII 脱敏）、校验结果、是否逃逸、退出原因、耗时、峰值内存、退出码、快照摘要、行数 | `app/tools/bill_analysis.py` |
| 熔断 | 有逃逸意图的代码计入 `tool_violation`，同一会话 2 次降为只读 | `app/tools/bill_analysis.py` 调 `breaker.on_tool_violation` |

### 6.2 测试证据

| 测试 | 用例数 | 内容 |
|---|---|---|
| `tests/redteam/test_sandbox_escape.py` | 70 | 静态拦截 36 条（import os / subprocess / socket / urllib、importlib、`__class__.__mro__` 链、`__subclasses__`、`__globals__`、open 读写文件、eval / exec / compile、getattr 拼字符串、读环境变量等）；运行时拦截 14 条（无限循环、3 种内存炸弹、递归炸弹、超大输出、修改快照、输出格式不对等）；**假设 AST 被绕过**的 9 条（直接把恶意代码送进子进程：os.system、os.open 读文件、写文件、列目录、fork 炸弹、socket 联网、再次 exec 等，靠审计钩子和资源限制拦住）；逃逸意图标记 5 条；无害错误不算逃逸 3 条；内存炸弹在限额附近被结束；子进程看不到密钥；逃逸计入熔断 |
| `tests/test_sandbox.py` | 34 | 正常分析结果和数据库直接计算一致（工作日 vs 周末外卖、月度咖啡趋势）；输出契约拒绝 14 种不合规输出；快照脱敏且不可修改；模型改代码后重试；规则模式提示不可用；审计记录 |

**结果：逃逸测试 70 条全部拦截。**

### 6.3 残余风险

1. **子进程沙箱不等于容器隔离**。没有网络命名空间和文件系统隔离，联网、读文件靠模块白名单和审计钩子拦，不是操作系统层面的隔离。生产环境应换成 gVisor / microVM（技术文档 R11）。
2. macOS 上内存靠父进程轮询，有几毫秒的滞后，单次大分配最多超出几十 MB 才被结束。
3. 机器繁忙时，死循环用例会接近 5 秒墙钟；测试断言接受 `cpu_limit` 或 `timeout` 两种结果。
4. 自由分析依赖模型写代码，规则模式下不可用。

## 7. 跨机制的残余风险
