## 2. 自动化测试

### 2.1 运行方式

```bash
cd apps/api && uv run pytest -q
```

测试使用临时数据库，模型路径用 `tests/conftest.py` 里的脚本化假模型（`fake`），不调用真实模型、不读 `.env` 里的密钥。`make test` 等价于上面的命令，`make redteam` 只跑 `tests/redteam/`。

每条测试从 2026-10-30 12:00（和演示基准日相同）开始，结果不随真实日期、开跑时刻和运行耗时变化；用例里用 `clock.travel` 快进。要在别的日期上跑，设 `DEMO_DATE`，如 `DEMO_DATE=2026-11-01 uv run pytest -q`（只换日期，时刻仍是 12:00）。

### 3.4 确定性工作流 vs 全部交给模型

11-01 模型出错的 7 次和 10-31 是同一类：「最近3个月花了哪些钱」出成支出总览或把转账也算进去（113,170.32 元 / 283 笔）；「我这一个月的消费记录」按自然月（10 月截至 30 日）而不是近 30 天算；「这个月交通花了多少」给了全部分类总览，没单独算交通（应为 541.11 元 / 33 笔）。下表是 10-31 那一轮的明细。

| 问题 | 模型的回答 | 应为 |
|---|---|---|
| 最近3个月花了哪些钱（3 次里 2 次） | 消费分类卡（只有汇总，没有明细） | 交易明细卡，近90天消费 269 笔，30,611.48 元 |
| 我这一个月的消费记录（3 次都是） | 按「本月」统计：2026年10月（截至30日）87 笔，11,949.72 元 | 按「近30天」：90 笔，12,019.20 元。这句本身有歧义，算口径不一致，不算答错 |
| 这个月交通花了多少（1 次） | 口径填成「支出」，本例合计相同 | 口径「消费」 |
| 我的支出总览（1 次） | 账单报告卡 | 消费分类卡 |

同一脚本每句 1 遍的复跑（同日）：工作流 12 / 12 全对，平均 0.01 秒；模型数字一致 9 / 12，平均 11.72 秒。另一处偏差是「最近3个月花了哪些钱」口径填成「支出」，合计 59,170.31 元（把转账、理财也算进去了），正确是消费 30,611.48 元。

结论：

- **速度**：工作流轮次比模型快两个数量级（0.02 秒 vs 9.3 秒），回归集平均从 10.6 秒降到约 4.2 秒 / 条主要靠它。
- **准确率**：模型的错误集中在「选哪个工具」「口径填什么」，数字本身都由账务引擎算，没有编造；工作流把这两步交给确定性规则，就不会选错。
- **确定性（置信度）**：工作流只接「整句话都认得全」的说法，认不全就交给模型，不存在猜对一半；同一句话每次结果一样，可复现、可审计。模型 3 遍里有 3 个问题前后答得不一样。
- **边界**：比较、趋势、平均、规则不认识的商户、两个同名收款人、「大额」这类要判断的说法，仍交给模型（`tests/test_workflow.py` 逐条覆盖）。

### 3.7 知识问答评测（WS9）

用例在 `apps/api/evals/kb.yaml`（问法刻意和知识库条目里的 q 不同）。10-31 知识库从 58 条扩到 101 条（新增监管法规要点 26 条、本行规则 19 条，见[技术文档 §5.9.2](02-产品技术文档.md#592-知识库组成)），评测集随之从 50 题扩到 **104 题**：91 题应命中知识库（原 43 题 + 本行规则新主题 22 题 + 监管 / 法规主题 26 题），12 题超出范围应拒答（新增股市预测、荐股、个税、车险、金价、信用卡提额），1 题个人数据应走工具。

**知识问句路由**（10-31）：扩库后的 33 条未命中里，14 条是「赎回理财的时候需要刷脸吗」这类话被赎回、订阅、解绑、下单工作流先接走，19 条是模型没查知识库就直接答，或者去调了办理工具。改法：

- 识别规则 / 条件类问句（`app/nlu` 的 `asks_rule`）：「…需要刷脸吗」「要不要验证」「能…吗」「怎么…」「为什么…」「会有什么影响」「在哪关」「要哪些材料」「是真的吗」。同时满足三个条件才算：没有金额、尾号、手机号这类办理槽位，不是「帮我… / 我要…」这种请求办理，知识库确实查得到。满足时排在业务意图之前（规则意图 `faq`），规划器也不接（不出候选商品、不进定时转账）。规则模式下评测集知识命中从 34 / 91 提到 82 / 91。
- 反例仍是办理：「给我妈转500行吗」（有金额）、「能帮我锁一下尾号6688的卡吗」（有尾号）、「怎么取消腾讯视频的自动续费」（点名了自己订的商户，走取消流程，卡上的商户指引同样来自知识库）、「我的卡丢了怎么办」（先建议锁卡止损）、「我的理财怎么样」「怎么理财」（问自己的账户 / 要建议）。
- 模型模式：整句和每个分句都是知识问句、而且知识库查得到时，先以模型的名义调一次 `kb.search`（走同一个工具网关，写审计和历史），只发知识域和常驻工具，模型照条文作答；提示词加第 10 条「问规则、条件、流程、原因先查知识库」。「挂失要钱吗？要的话帮我挂失 6688」这种带办理分句的不预查。模型再查一次、条目相同时不出第二张知识卡。
- 回归集 157 条规则模式前后一致（137 / 157，每条卡片都没变）。

扩库后最佳条目覆盖率阈值 `MIN_COVERAGE` 从 0.12 调到 0.15：「信用卡分期提额」这类知识库没有的问题覆盖率约 0.12，会误命中信用卡还款条目；评测集里命中题的最低覆盖率约 0.18。

**默认配置定为「混合 + 4B 重排 + agentic 重查」（11-01）**：

- **决定**：重排预设从 `Qwen3-Reranker-8B` 换成 `4B`；agentic 重查接入并默认打开（`KB_AGENTIC_RETRY`，要对话模型可用，规则模式不改写），实现见[技术文档 §5.9.2](02-产品技术文档.md#592-知识库组成)。
- **判断理由（团队）**：增加的耗时可以接受，并且能获得更可靠的答案；出于正确率和耗时的综合考虑，加上知识库回答正确的重要性，认为 agentic 重查有必要——以较少的耗时代价换取正确率的提升，比较有价值。对应的数据：重查只在原话没查到时触发（上表 4B 那组 271 题里 59 题，约 22%，每次中位多 2.2 秒），查到的问题不变慢；叠在 4B 上应命中的多答对 2 题（para-16「去日本旅游能直接刷这张卡吗」、para-69「机器人解决不了，能不能换个真人来跟我聊」），代价是超范围多误命中 2 题（para-oos-19「境外汇款到美国要多久」、para-oos-25「信用卡怎么申请提高临时额度」），总分持平。
